## 03:05 — Cram sheet: long legacy notes

The user asked whether a very long old note works. It mostly did, but there were two real bugs:
- A part Gemini skipped in a big batch was saved as one filler idea, permanently.
- One part over 2,000 words made `/tag` reject its whole batch, so every part in it got the fallback on every open.

Fixes: `/tag` returns `null` for skipped parts, and those aren't saved. Oversized parts aren't sent and just use the fallback. Batches are now 20 parts, 3 in parallel, and a failed batch no longer throws away the others. Checked on the mock build: a 150-part note with one 2,200-word part opened its sheet in about 2.5 s, with 149 parts tagged and saved and the big part on the fallback. Tests 16/16 + api 7/7, tsc pass.

## 04:20 — Part ids instead of positions

At the user's request (after the delete-part shuffle), parts got permanent `Chunk.id`s. Tries, exam tags, exam picks, ticks and feedback are now keyed by id, so deleting a part moves nothing. See the ADR 0001 addendum "part ids". The migration is free: old parts fall back to `String(position)`, which is where their data already lives; ids get filled in on the next write, and before any delete.

Checked on the mock build with an old-style note (no ids, data by position, number picks):
- Deleting part 2 of 4 left ids 0/2/3, deleted only that part's data, and C kept its history.
- Exams: [0,1,3] became ["0","3"], a B-only exam became empty, and the whole-note exam was unchanged.
- The cram sheet covered the right parts, and the form read old picks and saved ids.
- New notes get random ids.

Re-ran the full exam flow, the highlight check and the 150-part note: no errors. Tests 16/16, tsc and build pass.
