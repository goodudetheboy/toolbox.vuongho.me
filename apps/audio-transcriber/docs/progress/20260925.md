## 21:30 — Recording playback per segment + Lucide icons

What changed:
- Each transcript row has a play button that seeks the original recording
  to the segment's start and plays it. Clicking the playing row's button
  again pauses. The row under the playhead is highlighted. The play button
  also shows in edit mode. A native `<audio controls>` bar sits under the
  transcript header (`src/components/RecordingPlayer.tsx`).
- The recording comes from `src/lib/useRecording.ts`. It uses, in order:
  the queued `File` in this session, a `File` reopened from a saved File
  System Access handle, or a file the user attaches by hand. See
  [ADR 0002](../adr/0002-recording-playback-via-file-handles.md). IndexedDB
  goes to version 2 with a new `mediaHandles` store. Only handles are
  stored, never media bytes.
- Picking and dropping files go through `src/lib/filePicker.ts`:
  `showOpenFilePicker` / `getAsFileSystemHandle` when available, otherwise
  `<input type=file>`. The hidden inputs are gone from `DropZone`.
- All emoji icons are replaced with `lucide-react` (new dependency), in the
  header, dropzone, queue, history, transcript actions, and split/merge.
  The `←` back arrow, `×` close buttons and `▾` are replaced too.

Verified in dev (browser pane, `localhost:5174/audio-transcriber/`):
- The v1 → v2 IndexedDB upgrade creates `mediaHandles`.
- A history transcript seeded with an OPFS file handle loads on reload with
  no click (permission already granted). Clicking row 3's play button
  seeks to 6s and plays, highlights row 3, and changes the button to Pause.
  Clicking again pauses.
- A history transcript with no handle shows "Attach file…". Attaching (with
  a stubbed picker returning a handle) loads the player and saves the
  handle.
- Deleting the backing file and reloading shows the "moved, renamed, or
  deleted" error with Attach. Deleting a history item also removes its
  handle.

Not verified here:
- The "Reopen" permission-prompt state. OPFS handles are always granted, so
  a handle to a real disk file is needed in a real Chrome session.
- The Firefox/Safari fallback path (no handles).
- Queue path (in-session): dropped a WAV and faked the worker's
  CHUNK_DONE/DONE messages through a temporary dev-only hook (removed
  afterwards). The player loaded the queued file, and the row-2 play button
  seeked to 4s and highlighted row 2.

Decisions: [ADR 0002](../adr/0002-recording-playback-via-file-handles.md).

## 23:00 — Research: speeding up transcription (no code changes yet)

Benchmarked in the browser pane (dev server, cross-origin isolated, WASM
backend; the pane has no WebGPU adapter) on a 4.6-min TTS speech clip,
whisper-base.en q8. Throughput is × realtime; WER is against the known
script.

| Setup | × realtime | WER |
|---|---|---|
| Current: 60s pre-chunks + pipeline 30s/5s stride, 4 threads | 8.5 | 6.0% |
| Whole file through pipeline 30s/5s stride, 1 / 2 / 4 / 8 / 16 threads | 5.3 / 7.6 / 7.8 / 9.0 / 7.8 | 1.1% |
| N workers over contiguous ranges (5s pad, naive merge): 2×4 / 4×4 / 4×2 / 8×2 | 8.6 / 8.9 / 11.1 / 12.1 | 5.5–7% |
| 4×1 / 8×1 workers | 13.0 / 15.4 | 6.2 / 7% |
| 2×8 (oversubscribed) | 5.6 | 5.5% |

Findings:
- The 60s hard pre-chunks cost accuracy: 6.0% WER vs 1.1% for letting the
  pipeline's overlapping windows cover the whole file, at similar speed.
- More threads per ORT session barely help beyond 2. The autoregressive
  decoder is the bottleneck. Many single-threaded workers scale better:
  8×1 is about 1.8× current. It's sublinear on this short clip (pad
  overhead, load imbalance) and should do better on long files.
- transformers.js chains all inference calls within one JS context
  (`webInferenceChain` in `backends/onnx.js`) and runs ASR windows one at
  a time, with no `batch_size`. Parallelism therefore has to come from
  multiple workers.
- A naive range split + merge adds seam errors. Better: have workers
  decode subsets of the pipeline's own overlapping 30s windows and merge
  with `tokenizer._decode_asr`, the same merge the pipeline uses. That
  should match single-worker output.
- Energy-based "cut at silence" windows gave a Whisper repetition loop and
  a dropped sentence. Not worth pursuing without a real VAD.
- No failure retry today: any error marks the whole file failed.
  Already-emitted chunks stay in history; the rest is lost.

Not measured: WebGPU (no adapter in the pane), mobile devices.

## 23:45 — Parallel window decoding, retries, resume

What changed (see [ADR 0003](../adr/0003-parallel-window-decoding.md)):
- Dropped the hard 60s pre-chunks. The whole file is cut into the ASR
  pipeline's own overlapping windows (30s, 5s stride).
- The windows are decoded by a pool of `decoder.worker.ts` workers and
  merged in order with `tokenizer._decode_asr`. Pool size comes from
  `lib/poolSize.ts`: CPU gets ~1 single-threaded worker per physical core,
  memory-capped and max 8; iOS and WebGPU get 1.
- The coordinator moved from `workers/transcription.worker.ts` to the main
  thread (`lib/transcriber.ts`), keeping the same message protocol. Nested
  workers failed in the browser pane, even for a trivial script.
- Each window gets 3 attempts, and a crashed worker is respawned. On final
  failure the other windows finish first, the partial transcript is kept,
  and the queue item shows a Retry button that resumes only the missing
  windows (no re-extraction).
- Progress label: "Transcribing… N% · K workers". Progress updates replace
  the transcript instead of appending.

Verified (browser pane, WASM, 4.6-min speech clip):
- Dev: 8 workers, transcription phase 18.2s (15.3× realtime vs 8.5×
  before), 1.1% WER (same as single-worker), monotonic timestamps.
- Fault injection (temporary, removed): a worker crash on one job and a
  transient failure on every 4th job were both retried transparently. A
  permanent failure on the last window failed the file after the other
  windows finished (62/64 segments shown, Retry visible). Retry after the
  fault expired resumed at 93% and finished in 3.4s, with 1.1% WER and the
  same history entry.
- Production build via `firebase-tools serve`: decoder workers load from
  the bundled path, 8 workers, completes, no console errors. Local serve
  isn't cross-origin isolated, so this also covers the non-isolated case.
