## Migrated audio-transcriber into the toolbox as apps/audio-transcriber

User asked to fold their standalone `audio-transcriber` tool (its own repo
at `github.com/goodudetheboy/audio-transcriber`, deployed at
`audio-transcriber.vuongho.me`, soon to be sunset) into this toolbox at
`/audio-transcriber/`, as a 1:1 copy of its actual functionality/UI —
adapting only what's needed to fit the monorepo's conventions (same
pattern as `pdf-redactor`).

Cloned the source repo into scratch to inspect it rather than guessing at
its stack: Vite + React + TS, `ffmpeg.wasm` (audio extraction) +
`@huggingface/transformers` (Whisper, WebGPU with WASM fallback), IndexedDB
history, a dedicated Worker running the whole extract→transcribe pipeline.
1517 lines of source across `src/`.

Copied `src/`, `public/`, `scripts/copy-ffmpeg.mjs`, `index.html` verbatim,
then adapted only the integration layer:
- `vite.config.ts`: added `base: '/audio-transcriber/'`, kept its existing
  `worker`/`optimizeDeps`/dev-COOP-COEP settings as-is.
- `tsconfig.json`: switched to extending the shared
  `tsconfig.base.json` flat-style (matching `pdf-redactor`) instead of the
  original's project-references setup — the original's own lib/strictness
  settings were already a subset of the shared base, so no code changes
  needed for this.
- `package.json`: `build` script standardized to `tsc --noEmit && vite
  build`, same deps.
- Root `package.json` (`dev:audio-transcriber` script), `.claude/launch.json`
  (port 5175), `apps/homepage/src/App.tsx` (new tools-list entry).
- Added a "← Back to Toolbox" link in its header (the one thing every tool
  here has that standalone audio-transcriber didn't need), styled with the
  app's own warm color palette rather than copying pdf-redactor's dark-theme
  hex values — each tool keeps its own visual identity per the toolbox-wide
  [ADR 0001](../../../../docs/adr/0001-monorepo-npm-workspaces.md).

**Two real correctness bugs found and fixed while reading the source (not
cosmetic — the tool would have silently broken once served under a
subpath), plus one from testing the actual install:**

1. `transcription.worker.ts` hardcoded `/ffmpeg/` as the ffmpeg-core base
   URL. Fixed to `` `${import.meta.env.BASE_URL}ffmpeg/` `` — added
   `src/vite-env.d.ts` (`/// <reference types="vite/client" />`) since the
   original never used `import.meta.env` and had no such file. Verified the
   fix took effect by grepping the *built* worker bundle for the literal
   string Vite statically inlines — confirmed `/audio-transcriber/ffmpeg`
   appears in `dist/audio-transcriber/assets/transcription.worker-*.js`.
2. `public/manifest.json`'s `start_url`/icon `src` were root-relative
   (`"/"`, `"/icon.svg"`) — Vite doesn't rewrite raw JSON file contents in
   `public/`, only HTML attribute references, so these needed manually
   prefixing to `/audio-transcriber/...`. Confirmed via the built
   `dist/audio-transcriber/index.html` that Vite *did* correctly rewrite
   the `<link rel="icon">`/`<link rel="manifest">` `href`s it controls.
3. `scripts/copy-ffmpeg.mjs` assumed `@ffmpeg/core` lives in a local
   `node_modules` next to the script (`../node_modules/@ffmpeg/core/...`) —
   true in the standalone repo, false here since npm workspaces hoist it to
   the repo-root `node_modules`. First fix attempt
   (`import.meta.resolve('@ffmpeg/core/package.json')`) failed too — that
   package's `exports` field doesn't expose a `./package.json` subpath.
   Final fix: resolve the bare specifier (`import.meta.resolve('@ffmpeg/core')`)
   and derive `dist/esm` from the resolved entry file's directory. Verified
   directly (`node apps/audio-transcriber/scripts/copy-ffmpeg.mjs`) and via
   a full `npm install` from clean.

Added [ADR 0001](../adr/0001-audio-transcriber-coop-coep-headers.md): this
tool needs `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy`
(previously set via the standalone repo's `vercel.json`, now dropped) for
ffmpeg.wasm/transformers.js — scoped to `/audio-transcriber/**` in
`firebase.json` rather than site-wide, so no other tool is exposed to
COEP's cross-origin subresource blocking.

**Verification hit a real gap in the existing "test the production build"
workflow**: `npm run build && npm run combine && firebase-tools serve`
(the CLAUDE.md-mandated check) never applies `hosting.headers` at all —
confirmed with a deliberately broad `"source": "**"` test rule that still
didn't show up locally, in both `firebase serve` and `emulators:start`,
regardless of using a `target` or a bare `site`. Verified instead against
real Firebase Hosting infrastructure via a temporary preview channel
(`firebase hosting:channel:deploy audio-transcriber-verify --expires 2h`):
confirmed via `curl` that COOP/COEP headers are present on
`/audio-transcriber/**` responses and absent on `/` and `/pdf-redactor/`.
Deleted the channel afterward. Documented this gap in the toolbox's root
`CLAUDE.md` (it applies to any future `hosting.headers` change, not just
this one) and in this ADR's own addendum, so it isn't rediscovered the
hard way next time.

Exercised the actual app against that preview URL in the browser pane:
simulated a file drop (synthetic `DataTransfer`, same technique as
pdf-redactor's testing — no native file-upload action available) with a
generated 3-second WAV test tone. Model download and `Loading model…`
progress worked; hit `no available backend found` (WebGPU adapter
unavailable, WASM execution provider also unavailable) — but reproduced
the *identical* error against the live, unmodified, standalone
`audio-transcriber.vuongho.me` in the same browser pane, confirming this is
a limitation of the browser-pane sandbox itself (no real GPU/WASM-backend
support there), not a regression from the migration. Confirmed
`window.crossOriginIsolated === true` and `SharedArrayBuffer` available on
the preview, proving the COOP/COEP fix is actually in effect. Confirmed
the homepage lists "Audio Transcriber" and the back-link navigates to `/`
correctly.
