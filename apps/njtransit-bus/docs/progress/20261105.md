# 2026-11-05

## 13:10 — Faster cold start: timetable parse 3.5 s → 1.6 s

The user asked about the API's slow start. Cloud Run logs: about 12 cold starts
a day, each first request 11–14.5 s, the GTFS load 8.5–13 s of it (the service
scales to zero). Locally the load was 2.9 s downloading the zip from NJ Transit
plus 3.6 s parsing. The timetable was already loaded before the server listens,
so startup CPU boost already applied.

- `gtfs.js`: a small zip reader on Node's zlib (`unzipText`) replaces fflate's
  JavaScript inflate; `stop_times.txt` gets its own loop (`eachStopTime`) that
  cuts out just the four columns used, with `secs` parsing without splits;
  rows are grouped by trip with a counting sort (NJ Transit's rows are already
  in sequence within a trip; a trip that isn't gets sorted on its own) instead
  of a comparator sort of 1.8 M rows.
- Same output: stop search, nearest stops and three real trips' departures
  compared byte for byte, old vs new, on today's real timetable. New test for
  CRLF lines, quoted fields, a trip's rows split apart and stored zip entries.
- fflate is now a dev dependency (tests build fixture zips with it).
- Local cold start (download + parse) now ~5.1 s. ADR 0001 amended with the numbers.

Other options discussed, not done: cache the parsed timetable in Cloud
Storage (skips the NJ Transit download too), `--min-instances 1` (no cold
starts, but roughly $10–15/month against the $5 budget), and moving the API
to the user's Proxmox box (always on, via a Cloudflare/Tailscale tunnel;
would need an ADR).
