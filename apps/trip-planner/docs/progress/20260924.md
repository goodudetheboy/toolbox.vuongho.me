## Auth + Firestore sync + sharing, fully implemented

Picked up where
[2026-09-22](20260922.md) left off: the auth/sharing/sync plan in
[ADR 0001](../adr/0001-trip-planner-local-first-plus-planned-shared-auth-and-sync.md)
was blocked purely on GCP console access. That access now works, and the
user separately fixed a billing-account quota problem and completed a
one-time OAuth-consent-screen step in the Cloud Console (the one piece with
no public API — see the toolbox-wide log and the ADR addendum). Implemented
the full plan; see
[ADR 0001's addendum](../adr/0001-trip-planner-local-first-plus-planned-shared-auth-and-sync.md#addendum-2026-09-24-auth--firestore-sync--sharing-implemented)
for the complete design (including two deliberate deviations from the
ADR's original literal text, both explained there: how the read-only link
is actually secured, and how joining as an editor is verified server-side).

New: `src/lib/firebase.ts`, `src/lib/auth.ts`, `src/lib/cloud.ts`,
`src/components/AuthBar.tsx`, `src/components/ShareDialog.tsx`,
`firestore.rules`. Changed: `types.ts` (optional `cloud` field on `Trip`),
`useTrips.ts` (merges local + cloud trips, routes mutations to whichever
backs a given trip), `App.tsx` (auth wiring, share-link handling,
join-as-editor), `ItineraryView.tsx`/`ActivityCard.tsx`/`TripList.tsx`
(read-only mode, sharing/online affordances, cloud badge).

**Verified for real**, against the live `vuonghome` Firebase project, not
the emulator: signed in via a genuine email-link round trip (sent to and
retrieved from the user's real inbox), created a trip, went online, added
an activity, turned sharing on, opened the view link in a second signed-out
tab and confirmed it was fully readable with no edit controls, and — the
part that actually matters for security — sent an unauthenticated write
straight to the Firestore REST API for that trip and got back `403
PERMISSION_DENIED`, confirming enforcement is server-side (`firestore.rules`),
not just a hidden button in the UI. `tsc --noEmit`, `vite build`, and the
full workspace `npm run build && npm run combine` all passed; also
smoke-tested via `firebase-tools serve` against the real production bundle
per this repo's Worker/module-loading rule, since Firebase's SDK does its
own dynamic importing internally.

One rough edge found during testing, not a correctness bug: right after
clicking "Go online," the trip view briefly went blank in one browser tab
until a manual reload — Firestore's `onSnapshot` listener for "trips I own"
didn't appear to deliver its update promptly in that instance. A fresh page
load always showed the correct state immediately after, and the data in
Firestore was confirmed correct via direct API query throughout, so this
reads as a one-off client listener/timing hiccup rather than a data or
rules problem. Worth a closer look if it recurs, not blocking.

**Not done**: no UI to leave a trip's `editors` list or transfer
ownership; non-owner editors can edit a shared trip's content but not its
sharing settings. Neither was requested.

Per explicit user instruction, shipped straight to `main` (no PR) — same
as the original trip-planner build and its export/import addition on
2026-09-22.
