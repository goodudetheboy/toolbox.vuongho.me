## 12:45 — New tool: Trip Planner (local-first itinerary keeper)

User asked for a trip planner tool: a destination + date range, a
day-by-day itinerary of activities (start/end time, title, description,
category, free-text tags), plus Google/email-link sign-in (shared across
future tools), read-only/edit sharing, and Google-Docs-style live
collaborative sync.

Built `apps/trip-planner` (Vite + React + TS, same conventions as
`pdf-redactor`/`audio-transcriber`): `Trip { destination, startDate,
endDate, activities[] }`, `Activity { date, startTime, endTime, title,
description, category: 'sightseeing' | 'dining', tags[] }`. Data lives in
`localStorage` (`src/lib/storage.ts`) — small structured JSON, no need for
IndexedDB's binary-storage case from pdf-redactor's
[0003](../../../pdf-redactor/docs/adr/0003-local-history-via-indexeddb.md).
UI: trip list → create/edit trip (destination + date range) → itinerary
view rendering one section per day in the range, each with an add-activity
form and activity cards (time, title, category badge, tags, description,
edit/delete). Editing a trip's end date to a later day adds a new day
section automatically — that's the "add a date while editing the
itinerary" the user asked for, no separate control needed. Wired into the
homepage tool list, root `package.json` (`dev:trip-planner`), and
`.claude/launch.json` (port 5176).

**Checked for `gcloud`/Firebase access before deciding on the online
features (auth, sharing, real-time sync) — confirmed none is available in
this session**: no `gcloud` or `firebase` binaries installed, and
`npx firebase-tools serve --only hosting` fails immediately with "Failed to
authenticate, have you run firebase login?"; the underlying Google
OAuth/metadata calls are also rejected by this environment's outbound
network policy. Enabling the Google and Email Link sign-in providers and
creating a Firestore database are both console/login-gated steps with no
path from here. Per the user's own instruction, documented the planned
architecture instead of guessing at a partial implementation: see
[ADR 0001](../adr/0001-trip-planner-local-first-plus-planned-shared-auth-and-sync.md)
for the full plan (shared Firebase Auth across tools, per-tool Firestore
database per the toolbox-wide
[0004](../../../../docs/adr/0004-per-tool-backend-and-firestore-naming.md),
token-based read-only links vs sign-in-gated edit access, and — after
actually researching how Google Docs-style sync works — why per-activity
Firestore realtime listeners with last-write-wins is the right-sized
answer here instead of full OT/CRDT, since itinerary activities are
discrete records rather than free-flowing prose). The local `Trip`/
`Activity` shape already matches the planned Firestore document shape, so
none of today's work needs to be redone when that setup happens — it's
additive.

**Verification**: `tsc --noEmit && vite build` clean for trip-planner, and
a full `npm run build && npm run combine` across every app in the
workspace succeeded. `firebase-tools serve` couldn't be used to test the
production bundle (same auth-login gap as above), so served the combined
`dist/` with a plain static file server instead and drove it with a
scripted headless-browser smoke test (Playwright against the pre-installed
Chromium): created a trip, added an activity with a description/category/
tags, confirmed it's still there after a full page reload (localStorage
persistence), then extended the trip's end date by a day and confirmed a
new day section appeared with no activities yet. All passed.

**Not done / blocked**: Google/email-link sign-in, read-only vs edit
sharing links, and live multi-editor sync — all blocked on Firebase
console access as described above; plan is written up in
[ADR 0001](../adr/0001-trip-planner-local-first-plus-planned-shared-auth-and-sync.md)
for whenever that access exists.

## 13:20 — JSON export/import, shipped straight to `main`

User asked: since online storage still isn't available, add export/import
so trip data isn't trapped on one device, then ship straight to `main` to
test live (rather than opening a PR).

Added `src/lib/exportImport.ts`: "Export" (in `TripList`'s header) downloads
every trip as one `trip-planner-export-<date>.json` file; "Import" reads a
file back in via a hidden file input, validates its shape at runtime
(`isTrip`/`isActivity` type guards — rejects malformed files with a clear
message rather than crashing), and merges the result into existing trips by
`id` (`useTrips.importTrips`) — a matching id overwrites, a new one is
added. Documented as an addendum to
[ADR 0001](../adr/0001-trip-planner-local-first-plus-planned-shared-auth-and-sync.md)
since it's the interim answer to the multi-device gap that ADR already
called out.

Verified with the same Playwright-against-a-static-build technique as the
first session today: created a trip with an activity, exported it,
`localStorage.clear()`'d to simulate a fresh device, confirmed the empty
state, imported the exported file back in, confirmed both the trip and its
activity were restored exactly, then imported a deliberately-malformed JSON
file and confirmed it was rejected with "That file does not look like a
Trip Planner export." rather than crashing.

`tsc --noEmit && vite build` clean; full workspace `npm run build && npm
run combine` succeeded. Committed both the original trip-planner build and
this export/import addition, pushed the feature branch, then fast-forwarded
`main` directly to it (`3d8ae6e..a7dbefe`) per explicit user instruction —
no PR opened, since none was asked for. This triggers the real
`deploy.yml` production deploy on push to `main`.
