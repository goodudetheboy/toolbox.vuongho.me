# 2026-09-21

## Audio Transcriber added to the toolbox

User asked to fold their standalone `audio-transcriber` tool (its own repo,
deployed at `audio-transcriber.vuongho.me`, being sunset) into this toolbox
at `/audio-transcriber/`. The tool's own migration, bug fixes, and
verification are logged in
[apps/audio-transcriber/docs/progress/20260921.md](../../apps/audio-transcriber/docs/progress/20260921.md)
and its own [docs/adr/0001](../../apps/audio-transcriber/docs/adr/0001-audio-transcriber-coop-coep-headers.md).

Toolbox-wide integration for the new tool: `apps/homepage/src/App.tsx`
(new tools-list entry), root `package.json` (`dev:audio-transcriber`
script), `.claude/launch.json` (port 5175), and a `hosting.headers` rule in
`firebase.json` scoped to `/audio-transcriber/**` (the tool needs
COOP/COEP headers that no other tool needs — see its own ADR 0001 for why
it's scoped rather than site-wide).

## Real gap found: local `firebase-tools serve`/emulators never apply `hosting.headers`

While verifying the new headers rule above, found that neither
`firebase-tools serve --only hosting` nor `firebase-tools
emulators:start --only hosting` applies any `hosting.headers` rule at all —
confirmed with a deliberately broad `"source": "**"` test rule that still
never showed up locally. Real deployed Hosting does apply them (verified via
a temporary preview channel). Added a rule to the root `CLAUDE.md`: verify
any `hosting.headers` change with a preview channel deploy
(`firebase hosting:channel:deploy`), not the local serve/emulator commands —
this applies to any tool that ever needs a headers rule, not just this one.
