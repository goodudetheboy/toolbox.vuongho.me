## Fixed page-nav bug, added Ctrl+Z, delete-box, and IndexedDB history

User reported the redaction canvas goes blank after navigating forward
then back to a page (screenshotted "Page 1 of 17" showing empty), and
asked for: Ctrl+Z triggering Undo, click-a-box-to-delete-it (an (×) button
in the box's corner), and an upload history "to refer back to this later"
(suggested `localStorage`).

**Root cause of the nav bug**, found by instrumenting
[PageCanvas.tsx](../../apps/pdf-redactor/src/components/PageCanvas.tsx)
with `console.debug` and reproducing via the browser pane (synthetic
`DataTransfer` drop, since the built-in browser tool has no native file
upload) rather than guessing: `isReady` was a plain boolean. Navigating to
a page whose render happens to resolve fast enough that `setIsReady(false)`
and the later `setIsReady(true)` land in the same React batch nets out to
"no change" from React's perspective (still `true`, same as before) — so
React bails out of re-rendering entirely. But `canvas.width = base.width`
(which unconditionally clears a canvas's bitmap per the HTML spec, even
when set to its current value) had already run as a plain side effect
inside that same callback, un-tracked by React. Result: cleared canvas,
no repaint ever fires to fix it. Confirmed pdf.js itself was innocent first
— rendering the exact same page object twice, and the exact 1→2→1
sequence, both produced correct non-blank output in a raw pdf.js-only
test, isolating the bug to our effect/state design rather than the
library.

Fix: replaced the `isReady` boolean with `baseCanvas: HTMLCanvasElement |
null` as the state value itself — since `renderPageToCanvas` always
`document.createElement`s a fresh canvas, its object identity can never
coincidentally equal a previous value, so React can never bail out of the
redraw. Consolidated the canvas resize + draw into one effect keyed on
`[baseCanvas, rects, dragRect, selectedIndex]`. Verified via repeated
Next→Prev round trips in the browser, checking actual canvas pixel data
(`getImageData`) after each — non-blank every time now.

**Delete-a-box**: `PageCanvas` now hit-tests `pointerdown` against existing
rects (reverse order, topmost wins) before starting a new drag; a hit
selects that rect (blue outline drawn on canvas) and shows an absolutely-
positioned "×" button at its top-right corner (an HTML overlay div, not a
canvas-drawn hit target — much simpler than hand-rolling hit-testing on a
tiny drawn icon). `useRedactions` gained `deleteRect(page, index)`.
Verified end-to-end: draw a box, click it (outline + × appear), click ×,
box gone.

**Ctrl+Z**: a `keydown` listener in `App.tsx`, active only while editing,
maps `(ctrlKey || metaKey) && !shiftKey && key === 'z'` to `undoLast(page)`
with `preventDefault`. Verified live.

**History — pushed back on the `localStorage` suggestion**: explained to
the user why localStorage is the wrong fit for storing actual PDF bytes
(quota, base64 bloat, sync API) and used **IndexedDB** instead, keeping the
same "never leaves the browser" property the tool is built around — see
[ADR 0007](adr/0007-local-history-via-indexeddb.md). New
`src/lib/history.ts` (raw IndexedDB wrapper), `src/hooks/useHistory.ts`,
`src/components/HistoryPanel.tsx`. `App.tsx` now: saves a new entry once a
freshly uploaded PDF finishes loading, debounce-autosaves redaction edits
(400ms) against that entry, and can reopen any past entry (reconstructs a
`File` from stored `ArrayBuffer` bytes, restores `redactions` via a new
`useRedactions().replaceAll`). Given this tool exists specifically for
sensitive documents, made delete-one/clear-all first-class UI, not just a
"clear site data" afterthought. Verified live end-to-end including a real
page reload between save and reopen (not just in-memory): uploaded,
redacted, saw the entry in History with correct filename/page-count/
timestamp, reloaded the page, reopened it from History, and got the exact
same PDF with the exact same redaction box restored, pixel-identical
position. Also verified "Clear all history" empties the list.

Hit one non-bug snag: after editing `useRedactions.ts` and adding the new
`useHistory.ts`/`App.tsx` restructuring, Vite HMR briefly threw "Rendered
more hooks than during the previous render" — a hot-reload artifact from
the component's hook count changing while mounted, not a real defect;
confirmed by closing the tab and opening a fresh one, which loaded clean.

All four fixes typecheck clean (`tsc --noEmit`) and the full workspace
build (`npm run build`) still succeeds for both apps.

## Sped up export: Fast (JPEG) vs. Best Quality (PNG), parallel + progress

User asked why export was slow, then asked for fast/slow export options,
a progress indicator, and parallelization. Explained the mechanism first:
every page gets fully re-rendered at 150 DPI and re-encoded (not reusing
the lower-res preview canvas), sequentially, one page at a time — PNG's
lossless encoding being the main cost.

Rewrote [exportPdf.ts](../../apps/pdf-redactor/src/lib/exportPdf.ts):
`buildRedactedPdf` now takes `{ format: 'png' | 'jpeg', onProgress }`, and
processes pages through a concurrency-limited worker pool (4 at a time)
instead of a straight sequential loop — capped rather than unbounded
`Promise.all` to avoid a memory spike on very large documents, since each
150-DPI page is several MB of raw pixels. `Toolbar` now has two buttons,
"Fast Export" and "Best Quality", plus a live "Exporting X/Y…" label.
Added [ADR 0008](adr/0008-export-fast-jpeg-vs-quality-png-parallel.md)
since this revises 0005's PNG-only decision.

Explicitly noted (to the user and in the ADR) that JPEG doesn't weaken the
redaction guarantee — the box is opaque black pixels painted onto the
canvas *before* either encoding, so there's nothing under it for JPEG's
compression to leak; the only cosmetic risk is edge softness, not content.

Verified live: uploaded a 4-page doc, ran Fast Export and inspected the
downloaded bytes directly — found `/Filter /DCTDecode` (JPEG) objects;
ran Best Quality on the same doc — found none, confirming the format
toggle actually changes the embedded image codec, not just a label.
Generated a 30-page test PDF (served from a temporary `public/` file,
removed after) specifically to make the parallel pipeline's progress
observable: polled the page mid-export and saw "Exporting 4/30…" then
"Exporting 12/30…", confirming the worker pool genuinely processes
multiple pages concurrently. One test-only hiccup: adding a file under
`apps/pdf-redactor/public/` while the Vite dev server was running
triggered a full HMR page reload mid-export — a dev-server artifact from
the file-watcher, not a product bug; already had the progress and format
evidence needed before that happened.

`npm run build` clean for both apps after the change.
